Forge, start here

A goal harness for Claude Code. One command carries a one-line goal to a shipped product, with one decision left to you.

What changed in this version

3 October 2026 · Forge v2

Forge was tuned for Opus 5 and Fable 5, and its one full M run, vitrine, showed what that tuning cost. Measured out of its own transcripts by the corrected cost.mjs: $1,911 at list price, about 120 hours of wall clock, 153 dispatches, a lead whose context peaked near 1M tokens, and more agent time spent verifying (29.4 hours) than building (25.2). Older figures for the same run are higher because the old cost.mjs counted every API call twice; do not quote them. v2 is the lightest harness that keeps every quality constraint. Orchestration moved into code, deterministic checks come before judgment, and every seat pins its model. The bar did not move.

What you do differently

  • Make git work first. On macOS: sudo xcodebuild -license accept. Without it arm.sh refuses to arm, and commit.sh writes .forge/COMMIT-BLOCKED instead of committing.
  • Open the session on Opus 5.5 and leave effort alone. The project sets it to high. Never pass a model to a seat, and never enable /advisor.
  • Read the Fable block at the greenlight. It names the triggers and the cap. Approving is your consent to those calls, so change the cap there or not at all.
  • Approve, then walk away. There is nothing to paste. While the build runs the lead is idle and the ping is quiet. That is the design, not a stall.
  • After a crash, type /forge resume. The ledger on disk puts the build back at the right slice and the right rung.

Speed and cost gains are estimates until the v2 benchmark measures them: M two to four times faster, S about twice. The bar for merging v2 to main is concrete. On the same S goal, v2 takes at most half of v1's time and cost. On an M goal: 100 per cent PASS, lead peak context at most 300K, verifier hours at most builder hours, zero pin overrides in cost.mjs --models, and you judge the product market ready.

1. What Forge is

Forge is a set of configuration files that turns Claude Code into a product pipeline. You type /forge "a one-line goal" and answer three questions. The pipeline sizes the goal, researches the market, maps who will use the product, designs the screens, and writes a plan with an executable Definition of Done: a checklist where each line names the command, the judgment, or the operator proof that decides it. You approve that plan once, at the greenlight, and that is the only decision you make. After approval a background workflow builds the plan slice by slice behind a deterministic gate, and the run ends only when a fresh verifier confirms every line with recorded evidence. Then the lead ships it.

2. The mental model

Five primitives do all the work. None of them require programming to understand, but each answers a real weakness of a single AI session.

The lead session and its context window

When you run claude, you get one conversation with one model. Everything it reads, every file, every command output, accumulates in its context window: a finite working memory. When the window fills, the session summarizes itself and details get lost. The session driving a forge run is called the lead. Forge treats the lead's memory as unreliable by design, which is why state lives in files, not in the conversation, and why the build runs in a workflow rather than in the lead's own turns.

Subagents

The lead can delegate a task to a subagent: a second, separate conversation with its own empty context window, its own instructions, and a restricted set of tools. The subagent works, reports back one answer, and its context is discarded. A separate context beats a longer one for two reasons: the noise of a long investigation never pollutes the lead, and a fresh judge has no memory of writing the code it now grades. Forge defines seven seats in .claude/agents/, and each pins its own model and effort, so none inherits the session. See the subagents reference.

Hooks

A hook is a shell script Claude Code runs automatically at a fixed point in the session lifecycle: before a command executes, after a file edit, when the session tries to stop. Hooks do not ask the model to behave; they run regardless of what the model wants, which makes them the deterministic layer. A hook that exits with code 2 can block the action it guards. Forge wires nine hook registrations in .claude/settings.json to the scripts in scripts/. See the hooks reference.

Skills

A skill is a markdown file of knowledge or procedure that loads into context only when needed, so it costs nothing until it is used. Forge keeps its quality bar, design runbook, stack defaults, deploy runbooks, launch checklist, compliance triggers, and workflow rules as seven skills in .claude/skills/. See the skills reference.

Workflows

A workflow is a JavaScript file that spawns and coordinates subagents with its control flow in code. A loop the lead ran turn by turn would grow the lead's context on every pass; a loop in a script costs the lead one launch and one summary. Forge keeps two in .claude/workflows/, and only the lead runs them. See the workflows reference.

One more term you will meet: MCP servers connect Claude Code to outside tools over the Model Context Protocol. Forge uses one, Claude Design, for the design phase.

The four failure modes

Everything above exists to beat four ways an autonomous session fails:

Failure modeWhat it looks likeWhat answers it
Agentic lazinessThe session stops at partial progress and declares victoryThe Stop gate: dod-gate.sh blocks the turn from ending while armed rubric lines sit unchecked. The last line, V0, closes only when the final verifier rules that every other line holds
Self-preferential biasThe model grades its own work and finds it excellentgate.mjs, which runs commands rather than opinions, and the verifier: fresh context, never the builder's reasoning, and a holdout suite the builder never sees
Goal driftConstraints quietly vanish across context compactionThe state files: snapshot.sh saves them before every compaction, rehydrate.sh reloads them at every session start, and the compact policy in CLAUDE.md names what must survive
Bar driftA check is quietly edited until it passesarm.sh pins the approved rubric to a commit, and dod-check.mjs runs every check from that commit, so an edited command is ignored

3. Setup on a fresh machine

Each step ends with what correct output looks like, so you know it worked before moving on. Commands are for macOS or Linux.

  1. Install Claude Code and check the version. 
    npm install -g @anthropic-ai/claude-code
claude --version

    Expect 2.1.288 (Claude Code) or later. v2 was built on 2.1.288 and relies on per-seat effort, full model ids, and workflows that pin model and effort on every agent.

  2. Sign in. Run claude once in any folder; it opens a browser to authenticate.

    Expect the interactive prompt to load with no authentication warning. Type /status to confirm the account, then /exit.

  3. Check node and git. 
    node --version
git --version

    Expect a version string from each. If git prints an Xcode license message instead, run sudo xcodebuild -license accept and check again. This step is not optional: arm.sh refuses to arm without working git, and commit.sh writes .forge/COMMIT-BLOCKED instead of committing.

  4. Authenticate the GitHub CLI (deploys and private repos need it). 
    gh auth status

    Expect Logged in to github.com account .... If not, run gh auth login and follow the prompts.

  5. Clone the harness and enter it. 
    git clone git@github.com:lbtbly/agentic-goal-harness.git
cd agentic-goal-harness

    Expect a normal clone. Everything below runs from this folder.

  6. Make the scripts executable. 
    chmod +x scripts/*.sh

    No output is success. ls -l scripts/ should show -rwxr-xr-x on every .sh file.

  7. Add the Claude Design MCP server (documented command, user scope, added once for all projects), then sign in to it. 
    claude mcp add --scope user --transport http claude-design https://api.anthropic.com/v1/design/mcp

    Then inside a claude session run /design-login and complete the browser login.

  8. Verify everything. 
    claude mcp list | grep design
bash scripts/selftest.sh

    Expect claude-design: https://api.anthropic.com/v1/design/mcp (HTTP) - ✔ Connected and a selftest ending in selftest: all checks passed. Inside a session, /mcp should list claude-design, /agents should list the seven seats (scout, designer, design-critic, architect, builder, verifier, oracle), and typing / should offer forge plus the two workflows, build and design-directions. You never launch either by hand: the lead does, with the args they need.

After any Claude Code update, run bash scripts/selftest.sh once. It re-checks every hook script, the gate states, the model pins, the settings file, and the workflow syntax, and it simulates the build workflow's ladder with agents stubbed. It exits non-zero when anything drifted. Platform updates are when drift happens.

4. Your first run

Run this once interactively on a throwaway goal before trusting the pipeline with a real one. From the folder that holds the harness, make an empty project, copy the harness in (each product repo carries its own copy of the hooks, seats and scripts), and stamp the copy so drift shows up later:

mkdir moon-test && cd moon-test && git init
cp -R ../agentic-goal-harness/.claude ../agentic-goal-harness/scripts \
      ../agentic-goal-harness/CLAUDE.md .
node ../agentic-goal-harness/scripts/manifest.mjs sync . --adopt
claude

Open the session on Opus 5.5 with /model claude-opus-5-5, and leave effort alone: the project settings already set it to high. You do not pick models for the seats. Each pins its own, and the lead never overrides them. Fable never runs the session; it runs only as the oracle.

Then, at the prompt:

/forge "a one-page site that shows the current moon phase"

What you will see, phase by phase:

  1. Intake. Three questions appear as a form: done level, hard constraints, taste references. Answer them. Then check that your words landed: cat .forge/BRIEF.md should show the goal line and your three answers under their headings. This is the first check headless testing cannot prove, so look at it yourself.
  2. Size. The lead decides it in one line and records it in .forge/RESUME.md as Size: S, <reason>. This goal sizes S, so there is no scout and no research. If you answered "runs locally", there is no design phase either: the architect writes a four-line direction card instead. Simple stays simple.
  3. Plan. The architect writes .forge/PLAN.md (the stack, the checks the gate will run, one or two slices), .forge/DOD.md, .forge/PREFLIGHT.md, and the holdout suite. Read the rubric: every line ends in check:, judge: or operator:, and the last line is V0 | final verifier PASS.
  4. Greenlight. The run enters plan mode and presents the plan, the full rubric, and the pre-flight output. It also writes .forge/GREENLIGHT.md, a phone-sized summary with a Fable block: whether the plan audit ran (on this goal it will not) and the call cap. A desktop notification pings when the gate is waiting; that ping is the second check to confirm interactively. Do not approve. This test ends at the gate.
  5. Resume. Quit the session entirely, then reopen: 
    claude --continue
    The first thing in context is the FORGE STATE block injected by rehydrate.sh: the resume pointer, the unchecked rubric lines, and the line Awaiting greenlight. Nothing armed yet. That block appearing is the third interactive check. Nothing was re-asked, nothing was armed, nothing was built.

6. The build loop after approval

On approval the lead leaves plan mode and runs scripts/arm.sh, which commits the approved rubric, plan, checks and holdout, and writes .forge/ARMED: the pinned sha and the Fable cap. Then it runs node scripts/slices.mjs --open, writes .forge/BUILDING with its session id, launches build.js in the background, and ends its turn. The workflow's completion notice wakes it. Nothing is pasted and nothing is asked. While the workflow runs, every file edit triggers only a throttled commit (at most one per ten minutes), every Bash command passes guard.sh, and every named seat's finish lands one line in RUNLOG.md.

Inside the workflow, per slice:

  1. Builder. Records the pre-slice commit as the slice's base, builds inside the slice's declared scope, runs its own checks, and commits. It gets a clock: aim for 20, 30 or 40 minutes by size, and at twice that, commit and hand back partial.
  2. Gate. A Sonnet 5.5 agent at low effort runs node scripts/gate.mjs <slice> and reports its verdict verbatim. The gate runs the pinned typecheck, lint and tests, the build when declared, the slice's check lines through dod-check.mjs, and a scan of the slice diff for added suppressions. It never runs the holdout.
  3. Ladder. PASS: the slice is green. FAIL 1: the builder again, with the gate output. FAIL 2: the builder on Opus 5.5 at high effort. FAIL 3: stuck, back to the lead. A partial hand-back gets one continuation and then needs a re-slice; it never counts as a FAIL. UNKNOWN means something could not run: the slice is blocked on a prerequisite and never climbs the ladder.
  4. Milestone (M and L). After the slice that completes the core loop, the verifier re-runs every check closed so far, un-ticks any regression, and rules the judge lines in scope.

After the last slice the final verifier re-runs every check from the armed commit, walks the core loop as each actor in the grid, runs the holdout suite, sweeps the disqualifiers, and runs dod-check.mjs --rule, which ticks V0 only when every other line holds. A failed judge line is re-judged once in a fresh context first, because a model judge's false negatives run near a quarter. What still fails gets one fix round, then one more final verify.

On L, two or three builders may run at once when the architect put their slices in one group: disjoint scopes, no shared surface, the interface committed first, one base commit, and merges one at a time with the gate between them. The gain is wall clock, never tokens.

When the workflow returns, the lead removes BUILDING whatever the outcome, updates RESUME.md, and acts:

7. Memory and interruption

Every phase writes to .forge/ in the product repo. The session is disposable; these files are not. The build workflow is disposable too: it dies with the session that launched it, and everything it needs to resume is on disk.

The exact recovery sequence after a crash or a rate limit: when the window resets, run claude --continue in the product repo, read the FORGE STATE block, and if it shows BUILD INTERRUPTED, type /forge resume. Nothing else. Green slices are skipped, fail counts persist, and nothing is re-asked. If the block shows PARKED, the run is resting on the wait named there. If it shows COMMITS BLOCKED, git stopped working; section 10 has the fix.

8. The two workflows

A dynamic workflow is a script that spawns and coordinates agents with control flow in code. Forge keeps two in .claude/workflows/. Only the lead runs them, every agent() call pins its model and effort, and no workflow ever uses Fable.

WorkflowRunsDoes
build.json every armed run: after arming, after each re-slice, and on every /forge resumeone builder per open slice, gate.mjs after each, the ladder in code, the milestone verifier after the core-loop slice, and the final verifier with one re-judge and one fix round. Its args come from slices.mjs --open; fixIds runs only a fix round and a final verify. It returns done, or halted with the slice and the reason
design-directions.jsat DESIGN on M and L, unless the taste references already fix a single directionstratifies five design positions for this goal, generates one direction each in parallel, merges the best of all five into one, and iterates once. Retired with v2: verify-fanout.js, one agent per rubric line, now done by dod-check.mjs running every check line from the armed commit; and defect-sweep.js, whose fixer bypassed the gate and the commit. The six-pattern map went with them. Before adding a workflow, read the workflows skill: add one only when control flow would otherwise run through the lead's turns, or when the items are independent and number ten or more.

9. A machine that stays up

A build on an M or L goal can run for hours, and the build workflow lives inside the session: a session that dies stops the build until you type /forge resume. For a machine that must not sleep through it:

# keep the Mac awake while claude runs (ends when the command ends)
caffeinate -dims claude

# or run the session inside tmux so it survives the terminal closing
tmux new -s forge
claude
# detach: Ctrl+B then D    reattach later: tmux attach -t forge

Watching a run: open .forge/PROGRESS.html in any browser tab. It is a wallboard built to fill one screen with no scrolling: an overall completion estimate (gate work is 20 points, rubric lines the other 80, an evidence-recorded line counting half a verified one, and only a verified, reported run reads 100), the run duration and token total, the pipeline with the slices under it, rubric health per section, the evidence and dispatch feeds, and the latest captures. It is redrawn at every session end and every rate-limit checkpoint, and the page reloads itself every 15 seconds. During a long build, redraw it from a second terminal in the product repo with node scripts/progress.mjs. It is drawn from the state files and never edited by hand; if the page and a file disagree, the file wins.

Checking on a run from your phone: if the repo pushes to GitHub, read .forge/RESUME.md and .forge/RUNLOG.md in the GitHub app. GREENLIGHT.md is written phone-sized for exactly this: read it, then approve from your desk, where the full rubric is in front of you.

An unattended machine plus a broken ping is a silent failure. The desktop notification from notify.sh is the signal that the gate is waiting, a permission prompt is stuck, or the run has parked. It stays silent while BUILDING exists, because an idle lead is the design then. Before leaving a run unattended, trigger a notification once and confirm you can hear or see it. A run parked at a prompt burns no tokens but makes no progress either.

11. Glossary and customization

Lead
the main Claude Code session driving a forge run. It sizes, holds the gate, launches the build workflow, and ships.
Seat
one of the seven seats in .claude/agents/, each with a mandate, a pinned model and effort, and never-rules.
Oracle
the Fable 5.1 seat. Read-only, called only on a trigger listed at the greenlight, at most 3 times per run, never through /advisor.
Context window
a session's finite working memory; everything read or produced accumulates there.
Hook
a script the platform runs at a lifecycle point; exit 2 can block the action.
Skill
knowledge loaded on demand; costs no context until used.
MCP server
an external tool connection; forge uses claude-design.
Workflow
a script that runs agents with control flow in code. Forge has two, build and design-directions, and only the lead launches them.
Worktree
an isolated copy of the repo so parallel builders never collide (M and L goals, two or three at a time).
Slice
one vertical piece of the plan, crossing every layer, sized for one builder dispatch. Marked standard or light, and closes a named set of rubric lines.
Rubric, DoD
the Definition of Done in DOD.md; every line a checkbox with proof behind it.
check, judge, operator
the three kinds of rubric line: a command that exits 0 for pass and 1 for fail, a ruling by the verifier against a stated threshold, and a proof only you can supply. Judge lines are budgeted at S 8, M 25, L 50.
V0
the last rubric line, final verifier PASS. Only dod-check.mjs --rule ticks it, and only when every other line holds. The Stop gate never releases before it.
UNKNOWN
could not run. Never green and never a FAIL; it routes to a prerequisite rather than up the ladder.
Gate
gate.mjs, the per-slice check: pinned typecheck, lint and tests, the slice's check lines, and a suppression scan. Minutes, not hours.
Ladder
what happens on gate FAILs: retry with the output, then Opus 5.5 high, then stuck. The count lives in .forge/ATTEMPTS.json.
Evidence
a recorded command output, URL, or capture id in EVIDENCE.md; the only currency the verifier accepts.
Greenlight
the one human gate: plan, rubric, pre-flight and screens approved together, once, in plan mode.
Arm
arm.sh commits the approved rubric and writes its sha to ARMED. Every check runs from that commit, so the bar cannot be edited after approval. An amendment re-arms with a reason.
BUILDING
the marker the lead writes before launching build.js. While it exists the Stop gate and the ping stand down; a fresh session clears it and asks for /forge resume.
Park
a run resting on a named wait, recorded in PARKED. Not a question, not a failure, never a softened line.
Milestone
the one slice on M and L that completes the core loop. The verifier runs after it, not after every slice.
Actors grid
BRIEF.md's table of actor-job pairs. Replaces the role census and the persona panel. Every cell carries a provenance tag, and only the assumed ones reach you at the gate.
Band, stage
two separate proficiency axes on an actor row. Band is PIAAC digital skill, where Level 3 is five per cent of adults; stage is Dreyfus domain expertise. A Level 3 domain novice needs a different interface from a Level 1 domain expert, which is why they never collapse into one number.
LOUD, QUIET
the one element on a route that should pull the eye, and the region that goes quiet to pay for it. Declared in SCREENS.md so the blind design-critic can be wrong about it.
Squint
a capture reduced until only mass and contrast survive. A card-soup screen collapses into an undifferentiated grid; unblurred, the same screen reads as clean and modern to a model.
Capture triple
what every capture.sh call writes: the frame, an element tree with computed styles, and a meta with the command, the pins and a sha256. Seats pass ids, never bytes.
Anchor
the check that a page actually painted before anything about it is judged. A failed anchor records UNKNOWN, never a ruling on a blank frame.
Holdout
the verifier's acceptance suite, written before the greenlight and never shown to the builder. Adding more visible tests measurably widens the gap it exists to close.
Drift
the gap between this harness and the copy a project is running. One target ran a 601-byte Stop gate against a 3,947-byte original.

The commands worth knowing

bash scripts/selftest.shthe regression suite. Run it after every Claude Code update.
node scripts/seat-check.mjsevery seat's prose against its tool grant and pins. It once caught a blind critic holding Bash, which made it blind by request rather than by grant.
node scripts/cost.mjs --allper-seat cost, round-trips and peak context, read from transcripts that already exist. Each API call counted once, workflow agents included, Fable on its own line.
node scripts/cost.mjs --modelsthe models each seat actually ran against its declared pin. Exits 1 on an override.
node scripts/manifest.mjs check <target>which harness a project is actually running, orphaned files included. Never reports clean while anything differs.
node scripts/dod-check.mjs --show <ID>the armed text of a rubric line. --lint --size M checks format and the judge budget.
node scripts/slices.mjsevery slice with its ledger state. Read-only.
node scripts/attempt.mjs state <slice>how many times a slice has failed, its base commit, and which rung that puts it on.
bash scripts/capture.sh <id> <url>one capture, three files. Add --platform ios|android|engine off the web.
scripts/preflight.shwhat you still have to install, create or authorise. Reports, never gates.

Why a rule existsdocs/RATIONALE.md

One file is yours to write and nobody else's: .claude/skills/standards/SKILL.md holds three personal-rule slots, written as comments under "Personal rules". They currently carry value before the wall, motion calibrated to the category, and text that is designed rather than filled in. Every future rubric inherits whatever is there, so rewrite them where your taste differs before the first real run.
