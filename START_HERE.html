1. What Forge is

Forge is a set of configuration files that turns Claude Code into a product pipeline. You type /forge "a one-line goal" and answer three questions. The pipeline sizes the goal, researches the market, interviews synthetic users, designs the screens, and writes a plan with a per-goal Definition of Done: a checklist where every line is provable by a command or a screenshot. You approve that plan once, at the greenlight, and that is the only decision you make. After approval the build runs on its own, and it ends only when an adversarial verifier confirms every checklist line with recorded evidence, then ships the result.

2. The mental model

Four primitives do all the work. None of them require programming to understand, but each answers a real weakness of a single AI session.

The lead session and its context window

When you run claude, you get one conversation with one model. Everything it reads, every file, every command output, accumulates in its context window: a finite working memory. When the window fills, the session summarizes itself and details get lost. The session driving a forge run is called the lead. Forge treats the lead's memory as unreliable by design, which is why state lives in files, not in the conversation.

Subagents

The lead can delegate a task to a subagent: a second, separate conversation with its own empty context window, its own instructions, and a restricted set of tools. The subagent works, reports back one answer, and its context is discarded. A separate context beats a longer one for two reasons: the noise of a long investigation never pollutes the lead, and a fresh judge has no memory of writing the code it now grades. Forge defines seven subagents, called seats, in .claude/agents/. See the subagents reference.

Hooks

A hook is a shell script Claude Code runs automatically at a fixed point in the session lifecycle: before a command executes, after a file edit, when the session tries to stop. Hooks do not ask the model to behave; they run regardless of what the model wants, which makes them the deterministic layer. A hook that exits with code 2 can block the action it guards. Forge wires nine hook registrations in .claude/settings.json to the scripts in scripts/. See the hooks reference.

Skills

A skill is a markdown file of knowledge or procedure that loads into context only when needed, so it costs nothing until it is used. Forge keeps its quality bar, design runbook, stack defaults, deploy runbooks, launch checklist, compliance triggers, and workflow patterns as seven skills in .claude/skills/. See the skills reference.

One more term you will meet: MCP servers connect Claude Code to outside tools over the Model Context Protocol. Forge uses one, Claude Design, for the design phase.

The three failure modes

Everything above exists to beat three ways an autonomous session fails:

Failure modeWhat it looks likeWhat answers it
Agentic lazinessThe session stops at partial progress and declares victoryThe Stop gate (dod-gate.sh blocks the session from ending while rubric lines sit unchecked) and the native /goal evaluator, which re-checks the completion condition after every turn
Self-preferential biasThe model grades its own work and finds it excellentThe verifier seat: fresh context every dispatch, forbidden from editing source, ruling only with evidence
Goal driftConstraints quietly vanish across context compactionThe state files: snapshot.sh saves them before every compaction, rehydrate.sh reloads them at every session start, and the compact policy in CLAUDE.md names what must survive

3. Setup on a fresh machine

Each step ends with what correct output looks like, so you know it worked before moving on. Commands are for macOS or Linux.

  1. Install Claude Code and check the version. 
    npm install -g @anthropic-ai/claude-code
claude --version

    Expect a version of 2.1.233 or later, for example 2.1.233 (Claude Code). Dynamic workflows need 2.1.154+ and /goal ships in current versions.

  2. Sign in. Run claude once in any folder; it opens a browser to authenticate.

    Expect the interactive prompt to load with no authentication warning. Type /status to confirm the account, then /exit.

  3. Check node and git. 
    node --version
git --version

    Expect any recent versions. This machine showed v24.18.0 and git version 2.50.1.

  4. Authenticate the GitHub CLI (deploys and private repos need it). 
    gh auth status

    Expect Logged in to github.com account .... If not, run gh auth login and follow the prompts.

  5. Clone the harness and enter it. 
    git clone git@github.com:lbtbly/agentic-goal-harness.git
cd agentic-goal-harness

    Expect a normal clone. Everything below runs from this folder.

  6. Make the scripts executable. 
    chmod +x scripts/*.sh

    No output is success. ls -l scripts/ should show -rwxr-xr-x on every file.

  7. Add the Claude Design MCP server (documented command, user scope, added once for all projects), then sign in to it. 
    claude mcp add --scope user --transport http claude-design https://api.anthropic.com/v1/design/mcp

    Then inside a claude session run /design-login and complete the browser login.

  8. Verify everything. 
    claude mcp list | grep design
scripts/selftest.sh

    Expect claude-design: https://api.anthropic.com/v1/design/mcp (HTTP) - ✔ Connected and a selftest ending in selftest: all checks passed. Inside a session, /mcp should list claude-design, /agents should list the seven seats, and typing / should offer forge plus the four workflow commands (persona-panel, verify-fanout, design-tournament, defect-sweep).

After any Claude Code update, run scripts/selftest.sh once. It re-checks every hook script, both gate states, the workflow syntax, and the settings file, and exits non-zero on the first drift. Platform updates are when drift happens.

4. Your first run

Run this once interactively on a throwaway goal before trusting the pipeline with a real one. Make an empty project and copy the harness in (each product repo carries its own copy of the hooks and agents):

mkdir moon-test && cd moon-test && git init
cp -R ../agentic-goal-harness/.claude ../agentic-goal-harness/scripts \
      ../agentic-goal-harness/CLAUDE.md .
claude

Then, at the prompt:

/forge "a one-page site that shows the current moon phase"

What you will see, phase by phase:

  1. Intake. Three questions appear as a form: done level, hard constraints, taste references. Answer them. Then check that your words landed: cat .forge/BRIEF.md should show the goal line and your three answers under their headings. This is the first check headless testing cannot prove, so look at it yourself.
  2. Size. The router seat returns one letter with one reason. This goal sizes S, so scout and design are skipped: no research, no personas, no designer. Simple stays simple.
  3. Plan. The architect writes .forge/PLAN.md (stack plus vertical slices) and .forge/DOD.md, the rubric. Read the rubric: every line is a checkbox with a command or capture behind it.
  4. Greenlight. The run stops and presents the plan, the full rubric, and (on sized M and L goals) the design link, and it writes .forge/GREENLIGHT.md, a phone-sized summary. A desktop notification pings when the gate is waiting; that ping is the second check to confirm interactively. Do not approve. This test ends at the gate.
  5. Resume. Quit the session entirely, then reopen: 
    claude --continue
    The first thing in context is the FORGE STATE block injected by rehydrate.sh: the resume pointer, the unchecked rubric lines, and the line Awaiting greenlight. Nothing armed yet. with the exact /goal command to paste on approval. That block appearing is the third interactive check. The gate is still closed; nothing was re-asked, nothing was built.

6. The build loop after approval

On approval the lead creates .forge/ARMED, you paste the /goal line, and the loop below runs with no further questions. Every file edit triggers checks.sh (typecheck and lint feedback), every risky command passes guard.sh, and every subagent finish lands one line in RUNLOG.md.

7. Memory and interruption

Every phase writes to .forge/ in the product repo. The session is disposable; these files are not.

FileHolds
BRIEF.mdthe goal, your three intake answers, research, panel findings
DESIGN.mdinformation architecture, screen links, tokens, interaction notes (M, L)
PLAN.mdstack, slices, and the exact /goal line as its last line
DOD.mdthe rubric: checkboxes, three sections, disqualifiers
GREENLIGHT.mdthe phone-sized gate summary
EVIDENCE.mdappend-only proof lines: command outputs, URLs, screenshot paths
RUNLOG.mdappend-only black box: one line per subagent stop
RESUME.mdlast phase, current slice, next action; checkpoint stamps
REPORT.mdthe final report: links, evidence highlights, rubric state
ARMEDexists only between approval and ship; activates the Stop gate
snapshots/timestamped copies of the state files, taken before each compaction

The exact recovery sequence when a rate limit lands mid-run: wait for the window, run claude --continue in the product repo, read the FORGE STATE block, and if it says Gate active. If this is a fresh session, paste: followed by a /goal line, paste that line. Nothing else. The run picks up from RESUME.md's next action without re-asking anything.

9. A machine that stays up

A build phase on an M or L goal can run for hours. For a machine that must not sleep through it:

# keep the Mac awake while claude runs (ends when the command ends)
caffeinate -dims claude

# or run the session inside tmux so it survives the terminal closing
tmux new -s forge
claude
# detach: Ctrl+B then D    reattach later: tmux attach -t forge

Checking on a run from your phone: the state files are the status page. If the repo pushes to GitHub, read .forge/RESUME.md and .forge/RUNLOG.md in the GitHub app. GREENLIGHT.md is written phone-sized for exactly this: read it, then approve from your desk, where the full rubric is in front of you.

An unattended machine plus a broken ping is a silent failure. The desktop notification from notify.sh is the only signal that the gate is waiting or a permission prompt is stuck. Before leaving a run unattended, trigger a notification once and confirm you can hear or see it. If the machine will be truly unattended, check the run at intervals; a run parked at a prompt burns no tokens but makes no progress either.

11. Glossary and customization

Lead
the main Claude Code session driving a forge run.
Seat
one of the seven forge subagents, each with a mandate and never-rules.
Context window
a session's finite working memory; everything read or produced accumulates there.
Hook
a script the platform runs at a lifecycle point; exit 2 can block the action.
Skill
knowledge loaded on demand; costs no context until used.
MCP server
an external tool connection; forge uses claude-design.
Workflow
a script that orchestrates many subagents; runs as a slash command.
Worktree
an isolated copy of the repo so parallel builders never collide (L goals).
Slice
one vertical piece of the plan, crossing every layer, independently verifiable.
Rubric, DoD
the Definition of Done in DOD.md; every line a checkbox with proof behind it.
Evidence
a recorded command output, URL, or screenshot path in EVIDENCE.md; the only currency the verifier accepts.
Greenlight
the one human gate: plan, rubric, and screens approved together, once.
Arm, /goal
the native completion condition you paste at approval; a fresh model re-checks it after every turn.
Ultracode
a session mode where Claude orchestrates workflows by default; reserved for L builds.

One file is yours to write and nobody else's: .claude/skills/standards/SKILL.md holds three empty slots marked in comments. They are your personal rules, your taste in writing. Every future rubric inherits whatever you put there. Fill them before the first real run.
